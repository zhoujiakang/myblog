# 草稿文章发布转换 Spec

## 背景

Blog Desk 当前允许文章通过 Front Matter 中的 `draft: true` 标记为草稿，也允许保存和预览草稿。但现有“发布”动作没有把草稿转换为正式文章，导致文章即使完成了 Git 发布流程，仍可能被 Hexo 当作草稿处理，无法出现在正式博客页面中。

## 目标

- 保留新建文章默认为草稿的行为。
- 让草稿继续支持本地保存、应用内预览和列表标记。
- 发布草稿时，先让用户明确确认公开，再将其转换为正式文章。
- 只有完成 Hexo 构建、Git 提交和远程推送后，界面才显示发布成功。
- 保留文章的其他 Front Matter 字段和正文内容。

## 功能需求

- F1: 新建文章仍默认包含草稿状态，并在文章列表中显示“草稿”标记。
- F2: 草稿文章可以独立保存到 Hexo 项目，也可以在应用内预览；保存和预览不改变草稿状态。
- F3: 没有选中文章时点击“发布”不执行草稿转换、构建、提交或推送。
- F4: 选中的文章是草稿时，发布流程必须先显示明确提示：“这篇文章当前是草稿。发布后将转为正式文章，并推送到 GitHub Pages，是否继续？”，并提供“取消”和“转为正式文章并发布”两个选项。
- F5: 用户取消草稿发布时，文章内容、草稿状态和本地文件均保持不变，也不执行构建、提交或推送。
- F6: 用户确认草稿发布后，文章转换为正式文章；推荐移除 `draft: true`，并保留其他 Front Matter 字段和正文不变，然后继续现有发布流程。
- F7: 选中的文章不是草稿时，不显示草稿转换提示，但仍必须经过现有发布确认后才执行构建、提交和推送。
- F8: 绑定博客目录或配置远程仓库时检测当前分支、`origin` 和 upstream，并记录是否需要首次建立跟踪关系；首次经过用户确认的发布使用一次 `git push --set-upstream origin <当前分支>`，该关系建立成功后后续发布只使用普通 `git push`，不重复携带 `-u`。
- F9: Hexo 构建失败时不改变草稿状态；Git 提交或推送失败时不删除文章、不执行 reset、回滚或 force push，并保留本地文章和本地提交。
- F10: 只有远程推送成功后才显示“发布成功”；成功后刷新文章列表，使当前文章不再显示草稿标记。

## 非功能需求

- N1: 草稿转换只影响选中的文章，不改变其他文章、随心记、预览窗口和 Markdown 编辑器行为。
- N2: Front Matter 的字段顺序、其他字段和值以及正文内容应尽可能保持原样；至少不得因转换被删除或改写。
- N3: 绑定目录或检测远程仓库时不得自动向远程推送或绕过用户确认；不保存 Git 凭据，不向真实 GitHub 远程自动执行测试推送。
- N4: 继续兼容 macOS、Windows 和 Linux 的现有 Git 命令环境。

## 不做的事

- 不改变新建文章默认草稿的产品设定。
- 不把“保存”或“预览”视为公开发布。
- 不自动处理 Git 冲突、凭据、网络故障或远程历史不兼容。
- 不执行 `git reset`、force push 或删除文章文件。
- 不新增远程仓库配置、GitHub OAuth 或发布平台选择功能。

## 验收标准

- AC1: 新建文章仍是草稿，列表显示“草稿”；保存和预览后该状态仍存在。
- AC2: 无选中文章点击发布时没有构建、提交、推送或草稿文件变更。
- AC3: 草稿发布显示指定提示；取消后文章内容、Front Matter 和 `draft` 状态完全不变。
- AC4: 确认草稿发布后，源文件不再包含 `draft: true`，其他 Front Matter 字段和正文内容保持不变。
- AC5: 非草稿发布不显示转换提示，但仍需要普通发布确认。
- AC6: Hexo 构建失败时草稿仍保持原状态；Git 失败时文章和本地提交仍然存在，界面不显示发布成功。
- AC7: 推送成功后才显示发布成功，并刷新列表移除当前文章的“草稿”标记。
- AC8: 绑定目录时能检测并记录缺少 upstream；首次确认发布使用一次 `git push --set-upstream origin <当前分支>`，推送成功后再次发布使用普通 `git push`，不再使用 `-u`。
- AC9: 现有文章 Front Matter、随心记、Markdown 编辑器、应用内预览和 macOS 构建测试不回归。
