# 草稿文章发布转换 Plan

## 架构概览

沿用现有 Flutter 工作区和 Git 发布服务，增加草稿发布前的决策与转换步骤：

1. 绑定博客目录或配置远程仓库时检查当前分支、`origin` 和 upstream，并把首次设置 upstream 的需要状态纳入当前工作区状态；该检测本身不执行推送。
2. 发布动作首先检查当前项目和当前选中文章。
3. 对草稿文章显示独立的公开确认框；该框中的“转为正式文章并发布”就是本次发布授权，取消直接结束。
4. 对非草稿文章跳过转换框，进入原有发布确认框。
5. 用户确认后在发布编排中执行草稿转换、Hexo 构建、本地提交和上游推送。
6. 构建失败时恢复草稿文件的原始内容；提交或推送失败不做 reset 或回滚，并保留本地结果。
7. 推送成功后重新加载文章列表并显示成功状态；首次 upstream 推送成功后清除“需要设置 upstream”状态。

## 核心数据结构

### `PostDocument`

继续使用现有文章模型：

- `draft` 表示是否包含有效的草稿状态。
- `extra` 保存未参与编辑的其他 Front Matter 字段。
- `serialize()` 在正式文章状态下不写入 `draft: true`，从而移除草稿标记。

### `DraftPromotionSnapshot`

发布草稿时保存转换前状态：

- 文章文件路径。
- 转换前的完整文件文本。
- 转换前的内存草稿状态。

该快照仅用于 Hexo 构建失败时恢复原始草稿，不执行 Git 回滚。

## 接口

### 发布编排

- 输入：当前项目根目录、当前选中文章。
- 无选中文章：立即返回，不显示发布对话框。
- 草稿文章：先返回公开转换确认结果；取消时不产生文件或命令副作用。
- 非草稿文章：跳过草稿转换确认，进入普通发布确认。
- 输出：发布成功、取消或错误状态。

### 草稿转换

- 输入：选中的 `PostDocument`。
- 行为：保留 `extra`、其他 Front Matter 字段和正文，将 `draft` 设为 false，并序列化到原文章路径。
- 回滚边界：仅 Hexo generate 失败时使用快照恢复原始文本和草稿状态；后续 Git 失败保留文章和本地提交。

### `GitPushPlan`

沿用现有推送计划：

- 绑定目录时检测到已有 upstream：发布计划始终为 `push`。
- 绑定目录时检测到 `origin` 存在但没有 upstream：仅下一次确认发布计划为 `push --set-upstream origin <当前分支>`；成功建立跟踪关系后后续计划始终为 `push`。
- detached HEAD 或缺少 `origin`：在推送前返回可操作错误。

### 远程状态检测

- 绑定博客目录和配置远程仓库共用同一检测逻辑。
- 检测只读取 Git 状态，不执行 `git push`，不改变文章和提交。
- 若用户在应用外已经建立 upstream，下一次目录刷新重新检测后直接使用普通 `push`。

## 模块设计

### 工作区发布控制器

- 负责判断是否有选中文章。
- 负责显示草稿转换确认和普通发布确认。
- 只在用户确认后调用构建、提交和推送。
- 成功后重新加载文章列表，并保持当前文章选中状态。

### 文章模型与序列化

- 草稿状态仍由 Front Matter 的 `draft: true` 解析得到。
- 正式文章序列化时不输出 `draft: true`。
- 不改变其他字段和正文。

### Git 命令服务

- 保持现有 `generate`、`add`、`commit`、推送顺序。
- 继续使用项目根目录作为每条命令的工作目录。
- 不增加 force push、reset 或自动远程覆盖逻辑。

## 模块交互

```text
绑定/配置远程仓库
  -> 检测 origin、当前分支和 upstream
  -> 记录首次 upstream 是否待处理，不自动推送
  -> 点击发布
  -> 有选中文章？否：结束
  -> 当前文章是草稿？是：显示转正确认（同时作为发布确认）
       -> 取消：结束且不修改
  -> 确认：写入正式文章并保存快照
  -> Hexo generate
      -> 失败：恢复草稿快照并显示错误
      -> 成功：git add -> git commit -> git push 或首次一次性 git push --set-upstream
          -> 失败：保留本地文章/提交，显示错误
          -> 成功：清除待设置状态，刷新文章列表并显示发布成功
```

## 技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 正式文章标记 | 删除 `draft: true` | 与当前序列化器行为一致，避免新增 `draft: false` 噪音。 |
| 草稿确认 | 独立确认框 + 现有发布确认 | 明确区分“公开文章”和“执行 Git 发布”两个不可逆意图。 |
| 构建失败处理 | 使用完整源文本快照恢复草稿 | 满足构建失败不改变草稿状态，同时不使用 Git 回滚。 |
| Git 失败处理 | 保留本地文件和本地提交 | 提交可能已完成，不能用 reset 隐藏用户结果；用户可修复后重试。 |
| 推送策略 | 绑定目录时检测，首次确认发布只使用一次 `--set-upstream`，成功后普通 `push` | `-u` 是建立跟踪关系的初始化参数，不应污染后续发布。 |
| 检测副作用 | 绑定/配置时只检测，不自动推送 | 防止打开项目或配置远程仓库时产生未经确认的远程写操作。 |
