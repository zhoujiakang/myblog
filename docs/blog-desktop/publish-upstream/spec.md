# 首次 Git 推送上游配置 Spec

## 背景

Blog Desk 当前在发布流程最后执行普通 Git 推送。对于刚绑定的本地仓库，如果当前分支还没有配置远程跟踪分支，Git 会拒绝推送并提示用户手动设置 upstream。此次失败发生在本地提交已经完成之后，用户需要知道提交仍然保留，并能够安全地完成首次发布。

## 目标

- 让首次发布能够处理当前分支尚未配置远程跟踪分支的情况。
- 让已有远程跟踪关系的后续发布继续使用普通推送行为。
- 在推送前后清楚区分构建、提交和推送阶段，并提供可执行的失败建议。
- 保留已经生成的本地提交和文章源文件，不执行强制覆盖或自动回滚。

## 功能需求

- F1: 用户确认发布并完成构建、提交后，如果当前分支没有远程跟踪分支，应用应使用项目配置的默认远程和当前分支建立跟踪关系并完成首次推送。
- F2: 如果当前分支已经存在远程跟踪分支，应用应继续执行普通推送，不重复修改跟踪配置。
- F3: 如果默认远程不存在、当前处于 detached HEAD，或推送因凭据、网络、冲突等原因失败，应用应停止发布并说明具体原因及建议操作。
- F4: 推送失败时，应用不得删除、回滚或覆盖已经保存的文章源文件和本地提交。
- F5: 推送仍然必须发生在用户确认发布之后，不能因自动设置 upstream 而绕过确认。

## 非功能需求

- N1: 首次推送使用非强制方式，不得覆盖远程历史。
- N2: 远程名称、分支名称和 Git 输出应按现有系统能力处理，不在应用普通配置中保存凭据。
- N3: 行为应兼容 macOS、Windows 和 Linux 的 Git 命令环境。
- N4: 修复只影响发布阶段，不改变文章格式、预览、项目绑定和随心记目录结构。

## 不做的事

- 不新增远程仓库选择或 GitHub OAuth 配置界面。
- 不自动处理 merge/rebase 冲突，不执行 force push。
- 不替用户决定是否推送已经存在的本地提交。
- 不修改本次已经生成的本地提交内容。

## 验收标准

- AC1: 在存在 `origin` 的测试仓库中，当前分支没有 upstream 时，用户确认发布后首次推送成功，且该分支之后显示跟踪 `origin/<当前分支>`。
- AC2: 在已有 upstream 的测试仓库中，用户确认发布后仍能完成普通推送，跟踪关系不被重复改写。
- AC3: 默认远程不存在或当前不是分支时，发布在推送阶段停止并显示具体的修复建议，不执行强制推送。
- AC4: 模拟凭据、网络或远程拒绝导致的推送失败，确认文章文件和本地提交仍然存在，界面显示推送失败而不是发布成功。
- AC5: 未确认发布时不会执行构建后的提交或推送；首次 upstream 设置不会绕过确认。
- AC6: Flutter 测试、静态分析和 macOS 构建通过，且现有文章编辑、预览和随心记测试不回归。
