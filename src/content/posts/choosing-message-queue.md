选型是取舍。参数表上每一项长处都连着一项代价，能做的只是按自己系统的约束决定让掉哪一部分。我关心的是先划一条及格线，再看剩下的取舍分别对应哪一类场景。

## 先划一条及格线

每个系统的约束都不一样，同一项特性在这里是长处，换个场景就可能变成代价。所以先划出哪些产品至少及格，剩下的按自己的约束来定。

开源是第一条。真碰上一个影响业务的 Bug，至少还有机会自己改源码、快速修复或绕过去，不用干等官方下一个版本。这一条决定了出事的时候有没有主动权。

第二条是这几年仍然流行、社区还活跃。常见场景里的坑别人早踩过、修过，遇到的问题容易搜到解法；周边生态的集成也往往是现成的，Flink 内置了 Kafka 的 Data Source，换成一个小众产品就得自己写一个。冷门语言、冷门场景能不能找到客户端，也归在这一条里。

第三条是产品本身的硬指标：消息可靠传递，确保不丢；支持集群，单个节点宕机不会让服务不可用，也不会丢消息；性能足够好，能覆盖绝大多数场景。

这三条是筛选条件，不是打分项。达不到就出局，都达到了也说明不了该选谁；真正要权衡的是，每个产品把代价放在了哪里。

## 三个主流的差别

### RabbitMQ

Erlang 写的，最早为电信行业系统之间的可靠通信设计，也是少数几个支持 AMQP 协议的消息队列之一。它的定位很轻：开箱即用，部署和使用都省事，Slogan 就是 Messaging that just works。

比较特别的一层是 Producer 和 Queue 之间的 Exchange，按配置的路由规则把消息分发到不同队列，规则可以配得很灵活，甚至可以自己实现。真正需要这层路由能力的时候，它几乎没有替代。客户端支持的语言覆盖也很广。

不太行的是堆积。它把队列当管道，大量消息积压在设计里属于异常状态，真积压了性能会急剧下降。吞吐在三者里偏低，官方数据加日常经验大约是每秒几万到十几万条，够绝大多数场景，但对性能要求高的就不该选它。还有 Erlang 本身：语言小众、学习曲线陡，想做扩展或二次开发，得先想清楚以后由谁来维护。

### RocketMQ

阿里 2012 年开源，后来捐给 Apache，2017 年成为顶级项目，内部拿它扛过多次双十一，性能、稳定性和可靠性是压过的。我对它最深的印象是很难挑出刺：该有的功能几乎都有，性能、稳定性、可靠性都不缺，还在持续长。

在线业务的响应时延上做过不少优化，多数情况能到毫秒级；吞吐比 RabbitMQ 高一个数量级，每秒几十万条。Java 写的，贡献者多数是中国人，源码相对好读，中文社区活跃，遇到问题容易找到中文答案，要扩展也方便。

短板在国际化上：作为国产消息队列，海外的流行度不如另外两个，跟周边生态系统的集成和兼容程度略逊一筹。

### Kafka

LinkedIn 起源，现在是 Apache 顶级项目，最初是为处理海量日志设计的。早期为了极致性能做过不少牺牲：不保证消息可靠、可能丢消息、不支持集群、功能简陋，那个阶段严格说算不上一个合格的消息队列。后来这些短板逐步补齐，现在可靠性、稳定性和功能特性都能撑住绝大多数场景；网上还在说 Kafka 不可靠的对比文章，是过时的。

Scala 和 Java 写的，设计里到处是批量和异步。异步收发的吞吐靠这套设计拉得很高，但和 RocketMQ 没有量级上的差异，也是每秒几十万条。我记下的一个数字：在客户端并发足够、异步批量发送并开启压缩的压测里，极限能超过每秒 2000 万条。那是特定条件下的极限值，不是常态吞吐。

代价也出在批量上。发一条消息不会立刻发出去，要攒一批；Broker 里很多地方都是先攒一波再一起处理。所以同步收发的响应时延偏高，消息量不大时反而更明显，在线业务不适合它。它真正的长板在生态，大数据和流计算这一侧，几乎所有相关开源系统都优先支持 Kafka。

## 时延不等于吞吐

把三者放在一起容易看混的就是这一处。Kafka 的高吞吐是异步批量攒出来的，同步一条一条发反而慢；RocketMQ 吞吐和它没有量级差异，却在在线业务的毫秒级时延上专门优化过。RabbitMQ 的问题不是平时慢，是一积压就急剧下降——它的设计里本来就不打算承接堆积。

所以我给自己留的判据不是比吞吐，而是先看消息量有多大、是不是在线业务、允许不允许积压、周边要接哪些生态。这几个答案定了，候选范围就收得很窄了。

## 按场景落下去

消息队列不是系统主角，功能和性能都没有太高要求，只求开箱即用、好维护，对应 RabbitMQ。主要承载在线业务、在交易链路里传订单，看的是低时延和稳定性，对应 RocketMQ。要处理的是海量日志、监控信息、前端埋点，或者整条链路重度依赖大数据和流计算的组件，对应 Kafka。
