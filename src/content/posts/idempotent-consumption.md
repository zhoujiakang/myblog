确认和重试兜住了消息丢失，代价留在另一面：确认响应在回程丢了，发送方以为没送到，再发一次，Broker 或 Consumer 就多收一条。重复不是异常，是这套机制的必然结果，只能在消费端消化。

## 服务质量只有三档

MQTT 协议把传递消息的服务质量分成三档，这套分法对所有消息队列都适用：

- At most once，至多一次，允许丢消息，一般用在机房温度上报这类丢几条也无所谓的监控场景
- At least once，至少一次，不允许丢，允许重复
- Exactly once，恰好一次，不丢也不重

RocketMQ、RabbitMQ、Kafka 这些常用的消息队列，给出的都是 At least once。消息会不会重复，不是配置项能关掉的。

Kafka 文档里的 Exactly once 是另一回事，指的是流计算里每条消息恰好被计算一次，配合它的事务一起用，和这里说的传递服务质量不是同一件事。

## 幂等把重复消掉

幂等原本是数学里的说法：f(f(x)) = f(x)。搬到计算机里描述一个操作，意思是任意多次执行对系统产生的影响和一次执行相同。把账户余额设成 100 元，参数不变，执行几次结果都一样；给余额加 100 元，执行一次加一次，就不是幂等。

消费逻辑做成幂等之后，同一条消息消费一次和消费多次，结果一样，重复消息对业务就没有影响了。从结果上看，At least once 加上幂等消费，等于 Exactly once。

优先的做法是从业务逻辑本身入手，把操作设计成天然幂等的。做不到的时候，就得靠另外几层机制补。

## 唯一约束把重复挡在写入之前

给账户余额加 100 元这类不幂等的操作，可以改成往转账流水表里插一条记录：表里记转账单 ID、账户 ID 和变更金额，给转账单 ID 和账户 ID 建联合唯一约束，同一个转账单同一个账户最多只能插进一条。重复消费时第二次插入会失败，余额的更新挂在插入成功之后，就不会加两遍。

凡是支持 INSERT IF NOT EXIST 这类语义的存储都能这么用，Redis 的 SETNX 也能顶替唯一约束。

代价是业务里多一张表和一条写入路径，更新余额从一步变成两步。换来的是判断交给了存储的约束，不依赖消费端自己记状态。

## 前置条件让第二次更新不成立

另一条路是给数据变更加一个前置条件，满足条件才更新，更新时把这个条件一起改掉，重复执行到第二次时条件已经不成立。把「余额加 100 元」改成「如果当前余额是 500 元，就加 100 元」，消息体里带上当时的余额，消费时和库里的值比对，相等才改。

要更新的数据不是数值、或者变更逻辑比较复杂时，用版本号更通用：数据上带一个版本号，消息里也带上，比对一致才更新，更新完把版本号加一。

这类做法的前提是比对和更新得落在同一个原子操作里。拆成先查后改，两条重复消息就有可能都通过检查。

## 记录并检查操作的难点

前两种都不适用时，还有适用面更宽的一种：给每条消息指定一个全局唯一 ID，消费前先查这个 ID 有没有被处理过，没处理过才更新数据，然后把状态置成已消费。也叫 Token 机制或 GUID 机制。

适用面宽，实现也重，两个难点是明确的：全局唯一 ID 本身要兼顾简单、高可用和高性能，做法多，但都得让掉一部分；更麻烦的是「检查状态 → 更新数据 → 置为已消费」这三步必须作为一组操作保证原子性，否则并发下会出错——Consumer A 查到未处理、还没来得及置状态，Consumer B 也查到未处理，同一条消息就把账户加了两次 100 元。

把这三步收成一个整体，用事务或者锁都行，但分布式事务和分布式锁本身都不好做。所以这种办法一般不作为首选。

## 换到的是结果上的恰好一次

三种办法的差别在代价的位置：唯一约束把判断交给存储，多一张表和一次写入；前置条件不需要额外存储，但要求变更能表达成带条件的更新；记录并检查能兜住的场景更多，代价是全局 ID 和三步原子性。

它们解决的也不只是重复消息。HTTP 服务被重复提交表单、RPC 自动重试造成重复调用，都是同一个问题，把接口做成幂等就能兜住。

消息队列这边给到的是至少一次，恰好一次不是队列承诺的服务质量，是消费侧用幂等换出来的结果；换的代价落在每一次业务写入上。
