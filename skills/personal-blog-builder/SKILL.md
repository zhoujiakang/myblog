# 个人站：从零到上线

给用户搭一个属于他自己的站。核心不是"套一套好看的模板"，而是**先搞清楚他要什么，再按他要的东西搭**——栏目、风格、内容量都由他定，你负责把它做成能用的东西。

所有能读到的字都放在 `content/` 的 Markdown 里，用户之后改文案不碰代码。

---

## 先判断：用户要的是哪件事

不要一进来就开干。先认场景，不同场景读不同的文档：

| 用户说的 | 做什么 | 读哪份 |
| --- | --- | --- |
| "想做个个人网站 / 博客 / 作品集" | 从零建站 | 本文件往下走 |
| "帮我加一篇文章 / 改个文案 / 加个栏目" | 改已有站点 | `references/editing-a-site.md` |
| "页面白屏了 / 分享出去没图 / 构建报错" | 排错 | `references/pitfalls.md`（开头有症状速查） |
| "怎么上线 / 绑域名 / 怎么发布" | 部署 | `references/deploy-pages.md` |

判断不了的，问一句："你手上已经有站在跑了要改，还是从零开始做？"

## 主流程

### 1. 访谈

**读 `references/interview.md`，按里面的顺序问。** 三轮，每轮 3–4 个问题，一屏问完。

**每条问题都要带例子。** "你有哪些想记录的呢？比如文章、作品、照片，或者别的什么"比"你想要哪些栏目"能问出十倍的东西——例子让人从"从零想"变成"从我给的里认"。结尾那句"或者别的什么"不能省，例子要跨类型、一次 3–4 个（用法见文档第一节）。

这一步不能跳。用户说"我想做个个人网站"时，信息量接近于零——他要什么栏目、什么调性、有多少存货，全都不知道。跳过访谈直接搭，最后一定返工：改栏目动路由，改风格动一整层令牌。

访谈要拿到四件事：**给谁看**、**关掉页面记住哪句话**、**手上有多少存货**、**有没有审美参照物**。用户答不上来的，按文档里给的替代问法（给参照物 / 给二选一 / 给成品描述）兜住，不要卡在那里反复追问。

采访完用 `interview.md` 里的 brief 表回给用户确认，然后开工。

### 2. 定方案：栏目和风格都由用户定

**栏目不预设。** 不要一上来就开"作品 / 技能 / 文章"三栏——那是某一种站的做法，不是所有站的做法。先带例子问"还想放点什么"，再按存货量反推：存货少于 3 条的不做集合型（列表只有一项很空），存货多的才值得为它做详情页。给 2–3 个组合让用户挑或改，不要让他从零想。

栏目的四种类型、字段怎么定，见 `references/content-schema.md`。

**风格必须问，而且要让用户知道有得选。** 读 `references/styles.md`，做四件事：

1. **报库存**——现查 `src/styles/themes/` 有哪些（不要凭记忆，也不要把清单写进任何文档里），用气质和适用场景讲给用户听，不要只报文件名。
2. **问参照物**——"有没有哪个网站你打开觉得这样挺舒服"，不要问"你想要什么风格"（答"简洁大气"等于没答）。
3. **他没想法时念几个风格例子**——"纸质笔记本 / 终端 / 产品官网 / 杂志 / 手账"，一次 4 个以内。这些例子是帮他开口的引子，**可以随口、可以项目里根本没有，也不必和 `reference-build` 的视觉一致**；他挑中之后翻译成明暗 / 密度 / 强调再确认，别照原样实现。
4. **说清楚不锁死**——风格随时能换，现在不定也不影响开工。

**例子和库存别说混。** "项目里现成有一套 X" 和 "你说的那种也能做，但要新做" 是两句话，混着说，用户选了才发现没有。

用户说"都不喜欢"或"感觉不对"时，**不要问他想怎么样**，直接做 2–3 款候选让他挑（做法见 `styles.md` 的「用户说不好看」一节）。人对"不想要什么"的判断力远高于"想要什么"，给具体东西让他否，比让他描述有效。

用户说"你看着办"——用现成的那套开工，交付时说明用的是哪套、随时能换。**先交付再迭代，比卡在选风格上强。**

### 3. 搭骨架

按确定的栏目建目录、路由、视图。工程结构见 `references/architecture.md`。

需要具体实现时，按需取：

| 你要做的 | 去哪取 |
| --- | --- |
| 卡片 / 按钮 / chip / 时间线 / 代码块 / 空状态长什么样 | `references/design-fragments.md`（片段可摘，不用整份抄） |
| 网格、字阶、间距、动效、文案放哪 | `references/design-spec.md` |
| `.vue` / `.js` 怎么写 | `references/code-style.md` |
| 某个交互到底怎么实现的 | `assets/reference-build/` 里对应的单个文件 |

**`assets/reference-build/` 是参考实现，不是起点。** 不要 `cp -R` 整个目录开工——它的栏目和风格是某一套站的样子，复制过来要删改一半，比按需搭更慢，还会把不属于用户的栏目和审美一起带进去。要查的时候**只看需要的那个文件**，看完自己写。

骨架搭完先跑一次 `npm run dev`，确认空页面能开、导航能点、404 能显示，再往里填内容。

### 4. 填内容

在 `content/` 建栏目目录，写 `site.md`（全站配置）、`about.md`、`home.md`，再放首批条目。

字段名照 `references/content-schema.md`。**字段名写错不会报错，只是页面上安静地不出现**——这是最难排查的一类问题，写完对一遍。

三条纪律：

- **不替用户编内容。** 没有素材就留空，空状态本身是设计的一部分，比假数据体面。编出来的项目用户第一次打开就会要求删，还伤信任。
- **数字一律算出来**，不写死。栏目变了，统计口径也要跟着改（见 `content-schema.md` 第六节）。
- **文件名就是 URL**，定了别改。改了等于废掉别人已经分享出去的链接。

### 5. 定风格

把确定的风格落成一个主题文件：`src/styles/themes/<name>.css`，实现全部令牌，`global.css` 里 `@import` 指向它。

顺序是**底色 → 文字五级 → 强调色 → 线 → 圆角/阴影/底纹 → 字体**，反了会反复返工。令牌清单、配色推导、圆角取档、阴影配方见 `design-fragments.md`。

组件里不能出现裸色值、裸圆角、裸阴影。写死了换风格时会露馅：深色底配米白阴影、描边消失、卡片糊在背景里。

### 6. 分享封面与验收

分享封面：用户给了图就用 `python3 scripts/make_og_image.py -i <图> -o public/og-cover.png`（输出 1.91:1，左右用原图边缘无缝延伸）；没给图就留占位并说明。

**不要用 AI 重画用户已有的角色。** 角色会漂移（脸、衣服、配色对不上），生成的图还常带水印，用户一眼看得出不是原图。原图重排永远优先。

验收走一遍：首页 → 每个栏目 → 任一详情页 → 一个不存在的地址（看 404）→ 手机宽度。逐条过 `design-spec.md` 第七节的自检清单，至少确认：

- 文案全部来自 `content/`，组件里没有成句中文
- 空状态在对访客说话，不是"去 content/xx 加文件"
- 窄屏没有横向滚动
- 系统开了"减弱动态效果"时内容仍然可见

### 交付

说清楚三件事，别省：

1. **怎么改内容**——改哪个目录的 md，加一条要填哪几个字段。
2. **哪些还是占位**——`siteUrl`、分享封面、示例插画、空栏目，逐条列出来。别让用户以为已经完成。
3. **下一步能做什么**——加内容 / 换风格 / 上线。

## 和用户沟通

- **该问的一次问完。** 访谈三轮问清，别挤牙膏式追问，也别同一件事问两遍。
- **不该问的别问。** 技术栈、要不要 TypeScript、用不用 Tailwind、部署到哪个平台——这些是你的判断，不是用户的负担。
- **给判断，不要抛问题。** 用户说"不知道"时，给一个具体提案让他改，比再问一遍有效。
- **报进度说人话。** "首页和两个栏目能看了，风格还没定，你打开 dev 看一眼" 比 "已完成 60%" 有用。
- **不吹。** 不用"完美""全部完成"盖住没做的事。占位就说是占位，没做的就说没做。

## 边界

先确定能做什么：静态站点、内容外置到 Markdown、风格可换、GitHub Pages 上线。这套的范围就到这。

**做不到的，遇到了直接说**，别硬塞一个残废实现：

- 登录、评论、数据库、后台编辑 → 没有后端。接第三方（Giscus / Decap CMS）或换方案。
- 几百篇文章 + 全文搜索 → 构建期全量内联会变慢，该换 Astro / Next。
- 电商、预约、支付 → 完全超出范围。

**技术上不要做的**（原因见 `architecture.md`）：把 hash 路由改成 history、把内容改成运行时 fetch、把 `dist/` 提交进仓库、为了"看着专业"引入 Tailwind / Pinia / TypeScript。

说"这套不含 X，需要的话我们换方案"，比含糊答应最后交不出强。

## 建完之后（按用户接下来的需求再读）

| 用户接下来要 | 读哪份 |
| --- | --- |
| 加文章、改文案、调风格、改布局 | `references/editing-a-site.md` |
| 报错、白屏、分享图异常 | `references/pitfalls.md` |
| 上线、绑域名、日常发布 | `references/deploy-pages.md` |

这三份是建站完成后才用得上的。用户没提相应需求时不要读，也不要在交付说明里把部署流程整段讲一遍——等他要上线时再说。
