# 风格：先问，再定，最后才动手

风格是用户的事，不是你的默认值。**开工前必须问过**，并且要让用户知道三件事：现在有什么、可以自定义、现在不定也能改。

这篇讲怎么问、怎么给候选、怎么落地成文件。具体色值配方和圆角取档见 `design-fragments.md`。

---

## 一、两种"风格"，用途不同，别混

这个 skill 里有两批东西都叫"风格"，混着用就会出错：

| | **访谈例子** | **参考主题** |
| --- | --- | --- |
| 给谁看 | 用户 | 你自己，施工时 |
| 长什么样 | 一两句话的画面："米白底、字大、留白多、几乎不用色" | 一个 `.css` 文件，33 个令牌全填好 |
| 从哪来 | 现场想，可以随口，可以是项目里完全不存在的东西 | `src/styles/themes/` 里真实存在的文件 |
| 作用 | 让用户从"说不出"变成"这个不像、那个有点像" | 让落地有据可依：色阶怎么推、圆角取几档、阴影怎么配 |
| 要不要和项目一致 | **不必**。它只是语言层面的参照物 | **必须能构建**，满足对比度与令牌契约 |

两个错其实是同一个错——把它们说混了：

- **只报库存、不给例子**：用户面对一个陌生名字无从判断，只能回"你定吧"。
- **把例子说成"我们有"**：用户选了才发现要现场做，信任掉一档。

一句话记：**例子负责让用户开口，参考负责让你动手。**

所以**不要在这份文档里维护风格清单**——清单只存在于 `src/styles/themes/` 目录里，要报的时候现查（下一节）。

---

## 二、先报库存，不要凭记忆

**不要在这份文档里写"有哪几套"**——风格是会增加的，写死就会过期。要报的时候现查：

```bash
ls <项目>/src/styles/themes/
head -5 <项目>/src/styles/themes/*.css   # 每个文件头有气质与适用描述
```

给用户报的时候用**气质和适用场景**，不要只报文件名。下面只是话术示例——**实际内容必须按你查到的替换，别照抄这段**：

> "现在手上有一套：暖白纸感，字大、留白多，几乎不用颜色，只有一个金色做点缀。适合偏设计、写作、独立开发的调性。
> 这套是现成的，你要是看着可以就直接用；不喜欢也可以按你的喜好重新定，或者我做两三款给你挑。"

如果查出来有好几套，就按「气质 → 适合谁」一行一套列出来，让他挑。**报的套数必须和目录里的文件数对得上**——报了不存在的，用户选了就得现场造，等于骗他。

报完加一句**不锁死**：「风格随时能换，改一行的事，不用现在决定得很死。」

## 三、问风格：问参照物，也给例子

"你想要什么风格"这个问题，用户答"简洁大气""高级一点"等于没答——这两个词对每个人都成立，对施工没有指导意义。

先问参照物：

> "有没有哪个网站、App 或者产品，你打开觉得'这样挺舒服'？说个名字就行。"

用户想不出参照物时（很常见），**别退回开放题，念几个具体的风格画面让他认**。完整话术与挑选策略在 `interview.md` 第 2 轮第 ② 问，这里不重复维护一份。

念的时候，例子要在**不同维度上拉开**，否则四个例子其实是同一个选项：

| 维度 | 例子怎么拉开 | 落地时主要动 |
| --- | --- | --- |
| 明暗 | 白底 / 米白底 / 深底 | `--bg` 系列、`--ink` 系列、`--border-soft` |
| 冷暖 | 冷白 / 米白 / 微黄 | `--bg` 的色相 |
| 密度 | 大留白、一屏一件事 / 紧凑、信息密 | 间距、卡片内边距、字阶 |
| 字体性格 | 无衬线 / 大号衬线标题 / 全等宽 | `--font-display` `--font-body` `--font-mono` |
| 装饰 | 硬边框无阴影 / 淡阴影浮起 / 噪点底纹 | `--shadow-*` `--border-*` `--texture-image` |
| 强调用量 | 几乎无色 / 一处点缀 / 大面积色块 | `--accent` 系列的使用范围 |

用户挑中一个例子后，**不要照着原样实现**，先翻译成三件他能确认的事：

| 维度 | 问法 | 落到哪 |
| --- | --- | --- |
| 明暗 | "你更接近白底还是深色？" | `--bg` `--bg-card` `--ink` 系列 |
| 密度 | "喜欢松一点（信息少、留白大）还是紧一点（信息密）？" | 间距、卡片内边距、字阶 |
| 强调 | "几乎不用颜色，还是有个色做点缀，还是想要一块大面积的颜色？" | `--accent` 系列使用范围 |

**有些例子落不了地，要说清。** 用户说"像某某官网那样"，真实还原往往靠的是大量定制排版、动效和摄影，不是换令牌能到的。这时候讲明白能做到哪一部分、哪一部分做不到，别含糊答应——「能接近的是它的留白和字号关系，它那种大图滚动做不了，那需要逐页排」。

**人对"不想要什么"的判断力远高于"想要什么"**，所以给具体东西让他否，比让他描述有效。

## 四、用户说"不好看"或"都不喜欢"

这是最重要的分支。**不要问"那你想怎么样"**——他刚说完不好看，再让他描述想要什么，是把难题推回去，多数人会卡住或者给出"再高级一点"这种没法施工的答案。

正确做法：**做 2–3 款让他挑。** 你能一次给出具体东西，是因为你有判断力，这个判断力此刻就该用上。

注意这跟前面口头举的例子不是一回事：**口头例子只帮他说出方向，候选是真的做出来、能点开看的整站**。前者花三十秒，后者要花点时间——所以顺序是先例子、后候选，不要一上来就做三款。

### 候选怎么设计才有区分度

不要三款都是"换了个蓝色"。三款要在**同一个维度上拉开**，用户的选择才能给出明确信号：

| 策略 | 三款怎么变 | 适合 |
| --- | --- | --- |
| 保守（先试水） | 同一底色，只换强调色：金 / 蓝 / 绿 | 用户说"太素了"但没说别的 |
| 中等 | 变冷暖：暖白 / 冷白 / 米灰 | 用户说"感觉不对"但说不清 |
| 激进 | 变明暗：亮底 / 中间调 / 深色 | 用户说"太普通""想有个性" |

一次只变一个维度。同时变底色 + 圆角 + 字体，用户会说不清自己到底喜欢哪一点，下一轮你还是盲的。

### 怎么让用户看到

**别只用文字描述**——"冷灰底、蓝色强调"这种描述，用户想象不出来。

最快的方式是**真的做出来**：每个候选一个主题文件，改 `@import` 一行，dev 热更新，用户点一下就看到整站变化。

```
src/styles/themes/
├── candidate-a.css
├── candidate-b.css
└── candidate-c.css
```

让用户逐个看，选中哪个就把哪个改成正式名字（如 `main.css`），另外两个删掉。**留着会让下一个接手的人困惑**。

如果用户不在电脑前、或者不方便起 dev，退而求其次：用文字给**三件具体的事**（底色是什么色、松紧、强调色用在哪），并明确说"这一版你在浏览器里看一眼最快，文字说不准"。

### 候选的底线

即便是试着做的候选，也要满足：正文对比度 ≥ 7:1、组件里不出现硬编码、圆角档位 ≤ 3 种。**候选是"另一种成立的设计"，不是"随便糊一个让用户否掉"。**

## 五、风格怎么落地：主题文件

风格收在 `src/styles/themes/*.css` 里，组件不写死颜色和形状。这样做的好处很直接：换风格不用碰组件，试三款也不会把代码弄乱。

```
src/styles/global.css      结构（网格、字阶、组件、动效）—— 不随风格变
src/styles/themes/*.css    主题（颜色、字体、圆角、阴影、底纹）—— 可换可加
```

`global.css` 只有一行跟风格有关：

```css
@import './themes/<name>.css';
```

### 令牌契约

主题文件必须实现全部令牌，缺一个就会有元素回退到浏览器默认（黑字或透明底）：

| 分组 | 令牌 |
| --- | --- |
| 底色 | `--bg` `--bg-card` `--bg-hover` |
| 文字 | `--ink` `--ink-2` `--ink-3` `--muted` `--faint` |
| 强调 | `--accent` `--accent-soft` `--accent-wash` `--accent-halo` |
| 按钮 | `--btn-bg` `--btn-fg` `--on-accent` |
| 线与描边 | `--line` `--border-soft` `--border-strong` `--border-hover` |
| 形状 | `--radius-card` `--radius-btn` `--radius-chip` |
| 阴影 | `--shadow-card` `--shadow-lift` `--shadow-pop` |
| 底纹 | `--texture-image` `--texture-size` `--texture-position` |
| 字体 | `--font-cjk` `--font-display` `--font-title` `--font-body` `--font-mono` |

不需要底纹就写 `--texture-image: none`，不要整行删掉。

### 新增一套的步骤

1. 复制现有主题 → `themes/<新名字>.css`，改文件头注释（气质 / 适合谁 / 已知注意点）。
2. 按顺序填：**底色 → 文字五级 → 强调色 → 线 → 圆角/阴影/底纹 → 字体**。顺序反了会反复返工。从用户挑的例子出发时，用 `design-fragments.md` 的推导公式自己推色——例子只给方向（暖、密、几乎不用色），**不要回去抄那个站的具体色值**，那是别人的设计，抄了会撞脸。
3. 改 `global.css` 的 `@import` 指向新文件。
4. 跑一遍下面的自检。

### 换风格后的自检

```bash
npm run build
grep -rnoE "rgba\([0-9]+, [0-9]+, [0-9]+, [0-9.]+\)|#[0-9a-fA-F]{3,6}" src \
  --include=*.vue --include=*.css | grep -v "styles/themes/"
# 只应剩下 mask-image 用的 #000
```

- [ ] 首页：大标题、插画、入口卡、CTA 都正常
- [ ] 列表页：chip 激活态文字可读，时间线圆点与竖线可见
- [ ] 详情页：`meta` 行分隔线可见
- [ ] 404 页：按钮文字对比正常
- [ ] 640px 宽无横向溢出
- [ ] `prefers-reduced-motion` 下内容可见

## 六、五个容易踩的坑

**例子被当成规格。** 用户说"像终端"，不等于黑底荧光绿等宽字全套照搬——那只是他找来的一个方向。抓到方向后按自己的配方推，推出来通常比照搬好看，也不会撞脸某个知名产品。

**深色主题阴影失效。** 深底上淡阴影几乎看不见，层次必须靠描边撑（`--border-soft` 抬到 0.10 左右）。不抬描边，卡片会直接消失。

**只换颜色不换形状，等于没换。** 圆角、阴影、描边透明度也必须走令牌。写死在组件里的 `border-radius: 16px`，换到方角风格时会全程不配合。

**插画和主题打架。** 自带插画往往是暖白底或透明底。套冷色/深色主题时，一张暖底插画像一块贴错的纸——必须换图（保持文件名）或去掉首页大图。这个在深色候选里几乎必然遇到，提前跟用户说。

**对比度。** 强调色通常偏亮，白字放在上面会糊。`--on-accent` 要专门挑，不要默认用 `#fff`。正文对比度 ≥ 7:1，辅助 ≥ 4.5:1，12–15px 小标签也要 ≥ 3:1。

## 七、什么时候可以不定风格

用户说"先随便""你看着办"——这时**不要真随便**，也不要停下来追问。用现成的那套开工，但在交付时说清楚两件事：

1. 现在用的是哪一套（一句话描述气质）
2. 想换随时能换，改一行，或者让我再做几款给你挑

**先交付再迭代，比卡在选风格上强。** 用户看到实物之后的判断，比问十个问题都准。
