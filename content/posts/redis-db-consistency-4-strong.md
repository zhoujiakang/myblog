## 什么时候才需要更强的一致性

缓存和秒杀预扣允许一定的异步窗口。但涉及余额、额度等关键数据时，「最终能对上」可能不足以满足要求。

选型前要具体描述约束：是余额不能为负，还是每次读取都必须看到最新提交，或是多个存储必须原子提交？这些要求不同，不能用「强一致」三个字代替设计。

## 优先选择：收敛权威数据与事务边界

如果金额必须准确，我会优先让 DB 保存权威余额，在同一个事务中完成流水、余额变更与业务约束。Redis 用于非关键展示或查询加速，扣款、额度校验等决策读取权威存储。

即使 Redis 是副本，关键路径仍不能无条件读取它，否则旧值窗口依然存在。能否把约束收敛到一个存储，应先于引入分布式事务来评估。

## Seata AT 与 TCC 的边界

**Seata AT 不能直接把普通 Redis 操作变成可回滚的数据库分支。** AT 依赖支持本地 ACID 事务的关系数据库，通过数据源代理、undo log 等机制处理分支事务。

如果需要让 Redis 参与业务分支，可以评估自行实现 TCC：

- Try：按业务请求预留资源，并记录分支状态。
- Confirm：确认预留，重复调用也得到同一结果。
- Cancel：释放预留，同时处理重复取消、空回滚和悬挂。

Redis 分支要自行保证状态推进、预留资源的隔离和可恢复性。协调器不会替业务自动生成这些能力。TCC 可以和数据库分支配合，但补偿可能重试，普通读取也不会自动获得跨存储的统一快照。

因此，「包进一个全局事务，任一步失败就立即全部恢复，外部永远看不到中间态」不是可以直接作出的承诺。需要评估业务协议、隔离规则、持久化和故障恢复。性能代价也应通过具体工作负载测试，不能统一写成「损耗约 30%」。

## 本地消息表：保证 DB 提交后的通知最终送达

本地消息表适合解决「DB 业务数据已提交，但通知 MQ 或 Redis 失败」的问题。它提供最终一致的基础，不提供跨资源原子提交。

```sql
CREATE TABLE local_message (
  id BIGINT NOT NULL,
  biz_key VARCHAR(64) NOT NULL,
  event_type VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  retry INT NOT NULL DEFAULT 0,
  next_retry_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_event (biz_key, event_type),
  KEY idx_retry (status, next_retry_at)
);
```

```java
@Transactional
public void createOrder(Order order) {
  orderMapper.insert(order);
  messageMapper.insertPending(
      order.getId(), "ORDER_CREATED", toPayload(order));
}
// 中继线程：领取到期任务 → 发送 → 确认成功后标记完成。
```

这只是一次性订单创建事件的示例。若同一业务会多次产生同类事件，唯一键应使用事件 ID 或业务版本，避免误丢后续事件。

中继可能发送成功后、标记完成前崩溃，因此消息会重复，消费者必须幂等。还需处理并发领取、失败退避、积压监控与人工重投，不能用一个没有统计口径的「99% 一致」描述可靠性。

它也不能自动解决「先扣 Redis，再往 DB 插入消息」之间的缺口；秒杀预扣仍需要请求状态与恢复流程。

## RocketMQ 事务消息：需要可回查的本地结果

事务消息通过半消息、提交或回滚确认，以及异常情况下的事务回查，协调消息投递与本地事务结果。它的目标同样是最终一致。

生产者必须能按请求身份查询持久化的本地事务结果。未知或进行中的事务不能被随意判成失败；消息被投递也不意味着消费者业务已经成功。消费侧仍需事务、幂等和重试。

## Canal：通过 binlog 驱动副本同步

如果 DB 是权威存储，可以订阅 MySQL binlog，把已提交变更传给缓存消费服务。

```mermaid
flowchart LR
  A["MySQL"] -->|binlog| B["Canal"]
  B --> C["消费服务"]
  C --> D["删除或更新 Redis"]
```

这可以减少业务代码里的双写逻辑，但仍是异步同步。延迟取决于采集、传输与消费积压，不能保证恒定秒级。还需考虑断点恢复、重复消费、同一业务键的顺序，以及故障后的重建。

如果选择更新缓存，应通过业务版本等方式阻止旧事件覆盖新值；如果选择删除缓存，仍需考虑并发读的旧值回填。Canal 本身不会消除这些竞争。

## 对账：按业务状态修复

对账需要比较同一口径下的数据。纯缓存可以从 DB 重建，但读出 DB 值后再写 Redis，仍可能覆盖期间的新更新，因此通常优先失效，或使用版本校验。

秒杀库存则要计入有效的在途预扣，不能直接用 DB 剩余库存覆盖 Redis。修复过程需要水位、版本或暂停写入等协调机制，并保留审计记录。对账用于恢复和发现故障，不能替代关键路径的业务约束。

## 要求与边界对照

| 要求 | 优先方案 | 需要承认的边界 |
| --- | --- | --- |
| 普通缓存允许短暂旧值 | 提交后失效、可靠重试、TTL | 回填竞争、进程退出和副本延迟 |
| 秒杀异步受理 | 预扣状态、可靠消息、DB 约束、幂等释放 | 消息在途与结果未知，需要恢复状态 |
| DB 提交后通知不能丢 | 本地消息表或事务消息 | 最终一致，可能重复投递 |
| DB 变更驱动缓存 | Canal 等 CDC 链路 | 异步延迟、顺序与重放 |
| 金额等关键约束必须成立 | 单一权威存储的事务与约束 | 关键决策不能依赖异步缓存 |
| 确需跨资源协调 | 评估 TCC 等业务协议 | 自行落实隔离、幂等与恢复，不能默认全程同时可见 |

最终要交付的是清楚的业务契约：哪些状态可以被读到，哪里允许延迟，失败后由谁重试，怎样确认已经恢复。技术名词不能替代这些答案。
